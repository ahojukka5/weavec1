# Stable Core Architecture

This document defines the stable backend contract for the Weave compiler infrastructure.

## What is WIR?

WIR (Weave Intermediate Representation) is the stable boundary between frontend and backend in the Weave compiler architecture. It uses a simple S-expression syntax:

```lisp
(core-module
  (core-version 1)
  (decls
    (fn main
      (params)
      (returns i32)
      (do
        (return (const_i32 42))))))
```

WIR is intentionally:
- **Small and explicit** - minimal set of primitives
- **Backend-focused** - close to LLVM IR semantics
- **Stable** - conservative evolution, strong backwards compatibility
- **Auditable** - human-readable, no implicit transformations
- **Deterministic** - same input always produces identical output

## The Bootstrap Ladder

The Weave compiler uses a three-stage bootstrap:

### Stage 0: weavec0
- Hand-written LLVM IR assembly
- Located in `../weavec0/`
- Frozen implementation - no further changes
- Compiles WIR source → LLVM IR
- Contract: accepts `(core-module (core-version 1) ...)` syntax

### Stage 1: weavec1
- Written in WIR
- Located in `src/*.wir`
- Compiled by weavec0
- Primary development compiler
- Must produce identical LLVM IR to weavec2 (determinism guarantee)

### Stage 2: weavec2
- Self-hosted: weavec1 compiling itself
- Validates bootstrap correctness
- Must produce identical LLVM IR to weavec1 (bootstrap determinism)

## Bootstrap Determinism Guarantee

**Critical invariant**: For any valid WIR input, weavec1 and weavec2 must produce byte-for-byte identical LLVM IR output.

This is validated automatically in `build.sh` via `compare_bootstrap_outputs()`:
- Compiles all positive tests with both weavec1 and weavec2
- Diffs LLVM IR output for each test
- Build fails if any divergence is detected

Why this matters:
- Proves the compiler correctly compiles itself
- Detects non-deterministic code generation bugs
- Ensures LLVM IR fixtures remain stable
- Validates the bootstrap ladder is sound

## LLVM IR Fixtures

Each test has an expected LLVM IR fixture (`tests/*.expected.ll`):
- Generated by weavec1 (not weavec0)
- Used for regression testing
- Compared against actual output during build
- Must be deterministic and stable

Fixture testing ensures:
- Code generation doesn't change unexpectedly
- LLVM IR output remains auditable and readable
- Regressions are caught immediately
- Output format is consistent

When to update fixtures:
- Intentional codegen improvements (with justification)
- Bug fixes that change output
- New features that require new patterns

Never update fixtures to "make tests pass" without understanding why output changed.

## The Stable Backend Contract

### What WIR Provides

WIR defines a stable set of primitives:
- Integer types: `i32`, `i64`, `i8`
- Pointer type: `ptr`
- Boolean type: `bool`
- Void type: `void`
- Arithmetic: `add_*`, `sub_*`, `mul_*`, `div_*`, `mod_*`
- Comparisons: `lt_*`, `gt_*`, `le_*`, `ge_*`, `eq_*`, `ne_*`
- Control flow: `if`, `while`, `do`, `return`
- Functions: `fn`, `params`, `returns`, `call_*`
- Memory: `let`, `set`, `local_get`, `param_get`
- Pointers: `ptr_null`, `ptr_add`, `store_*`, `load_*`
- Externs: `extern` for C function declarations
- String literals: `const_string_ptr`
- Debug markers: `debug` (preserved in source, ignored in codegen)

### What Changes Are Allowed

The WIR contract evolves conservatively:

**Allowed changes:**
- Adding new operators (with explicit versioning)
- Improving error messages
- Internal codegen optimizations (if deterministic)
- Documentation improvements
- Bug fixes that correct incorrect behavior

**Prohibited changes:**
- Removing operators without multi-version deprecation
- Changing operator semantics
- Making output non-deterministic
- Breaking existing valid WIR programs
- Implicit transformations or magic behavior

### Version Management

WIR uses explicit versioning: `(core-version 1)`

- Version 1 is the current stable version
- Future versions (2, 3, ...) will support new features
- Older versions remain supported (frozen contract)
- Compiler must support all versions it claims to support

## Relationship to Surface Language

**Important**: WIR is not the end-user language. It's the compilation target.

```
┌─────────────────┐
│ Surface Language│  ← Future: macros, syntax sugar, type inference
│  (not yet impl) │
└────────┬────────┘
         │ lowers to
         ▼
┌─────────────────┐
│      WIR        │  ← Stable backend contract (this document)
│  (core-module)  │
└────────┬────────┘
         │ compiles to
         ▼
┌─────────────────┐
│    LLVM IR      │  ← Machine codegen target
└─────────────────┘
```

The surface language will:
- Provide high-level features (macros, pattern matching, etc.)
- Lower to WIR for compilation
- Be free to evolve rapidly
- Not affect WIR stability

WIR intentionally stays low-level and explicit. All surface features must lower to WIR primitives.

## Project Philosophy

The Weave compiler prioritizes:

### Auditability
- Human-readable intermediate representations
- No black-box transformations
- Explicit lowering from high-level to low-level
- Clear correspondence to generated LLVM IR

### Determinism
- Same input → same output, always
- No randomness in codegen
- Stable symbol names and ordering
- Reproducible builds

### Readability
- Formatted LLVM IR with clear comments
- Meaningful label names (`while.cond0`, not `label7`)
- Section markers in generated code
- Explicit types and operations

### Explicit Lowering
- No implicit conversions
- No magic operators
- No hidden allocations
- Programmer controls memory layout

### LLM-Friendly Structure
- Consistent formatting and naming
- Predictable code patterns
- Machine-parseable but human-readable
- Clear separation of concerns

## Stabilization Milestone

The core is considered stable when:

1. Bootstrap determinism validation passes
2. Integration tests cover feature interactions
3. LLVM IR fixtures are established and tested
4. This documentation is complete
5. Test categorization is clear
6. weavec0 contract is frozen

Once stable:
- WIR primitives are locked (version 1)
- LLVM IR output format is frozen
- weavec0 receives no more changes
- Surface language development can begin

## What Comes Next

After core stabilization:

1. **DO** implement surface language features:
   - Macro system
   - Pattern matching
   - Type inference
   - Syntax sugar

2. **DO** optimize the surface→WIR lowering:
   - Better error messages
   - Source location tracking
   - IDE integration

3. **DO NOT** change WIR primitives:
   - Keep the stable contract
   - Version carefully if needed
   - Preserve determinism

4. **DO NOT** add features to WIR itself:
   - WIR is intentionally minimal
   - Surface features lower to WIR
   - Backend remains simple

## Summary

The stable core provides:
- A frozen backend contract (WIR version 1)
- Deterministic code generation
- Auditable LLVM IR output
- Validated bootstrap correctness
- Foundation for surface language development

This stability allows frontend innovation without backend churn, while maintaining correctness guarantees through the bootstrap ladder and fixture testing.
