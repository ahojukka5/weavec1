# Core Stabilization Milestone

This document records the core stabilization milestone for the Weave compiler infrastructure.

## Date

May 21, 2026

## Milestone Definition

The **Core Stabilization Milestone** marks the completion of the core hardening pass, establishing WIR (Weave Intermediate Representation) as a stable, frozen backend contract. This is the foundation upon which all future surface language development will build.

## What Has Been Achieved

### 1. Bootstrap Determinism Validation ✅

**Implemented**: `compare_bootstrap_outputs()` function in `build.sh`

The compiler now validates that weavec1 and weavec2 produce byte-for-byte identical LLVM IR output for all test cases. This proves:
- The compiler correctly compiles itself
- Code generation is deterministic
- No non-deterministic bugs exist in codegen
- The bootstrap ladder is sound

**Impact**: Any divergence in bootstrap output will fail the build immediately, preventing non-deterministic behavior from being introduced.

### 2. Integration Test Coverage ✅

**Added Tests**:
- `55_integration_nested_control_flow.wir` - nested if + while + i64 arithmetic + mutable locals
- `56_integration_multi_function_chain.wir` - multi-function chains with forward declarations
- `57_integration_memory_flow.wir` - memory operations (malloc → ptr_add → store → load → free)

These tests go beyond single-feature unit tests to validate that features work correctly in combination. They catch interaction bugs that unit tests alone would miss.

**Impact**: Higher confidence in compiler correctness, especially for real-world usage patterns.

### 3. Architecture Documentation ✅

**Created Documents**:
- `docs/STABLE_CORE.md` - Defines WIR, bootstrap ladder, stable contract, project philosophy
- `docs/LLVM_FIXTURES.md` - Explains fixture testing system, workflows, best practices
- `docs/STABILIZATION.md` - This document, recording the milestone

**Impact**: Clear specification of what is stable and what is allowed to change. New contributors can understand the architecture and constraints.

### 4. Test Organization ✅

**Enhanced `build.sh`** with categorization comments:
- Basic Features (01-10)
- i64 Operations (11-13)
- Boolean and Pointer Basics (14-15)
- Memory Operations (16-18)
- Function Calls (19-22)
- i32 Arithmetic and Extended Features (23-33)
- Complete i32 Operator Coverage (34-40)
- Edge Cases and Control Flow (41-49)
- Negative Tests (50-53)
- Debug Features (54)
- Integration Tests (55-57)

**Impact**: Easy to understand test coverage and find relevant tests for specific features.

### 5. LLVM IR Fixture System ✅

All tests have expected LLVM IR fixtures (`*.expected.ll`) that are:
- Generated by weavec1 (the authoritative compiler)
- Validated on every build
- Checked into version control
- Reviewed in pull requests

**Impact**: Any codegen change is immediately visible and must be justified. Output format remains stable and auditable.

## What Is Now Frozen

### WIR Core Version 1 Contract

The following are **frozen** and will not change without explicit versioning:

- **Operators**: All current WIR operators (`add_i32`, `if`, `while`, `call_i32`, etc.)
- **Type system**: `i32`, `i64`, `i8`, `bool`, `ptr`, `void`
- **Syntax**: S-expression format `(core-module (core-version 1) ...)`
- **Semantics**: Behavior of all operators and control flow constructs

### weavec0 Implementation

- weavec0 (hand-written LLVM IR) is **frozen**
- No further changes will be made to `../weavec0/`
- It defines the WIR version 1 contract by implementation
- All future development happens in weavec1 (WIR source)

### LLVM IR Output Format

- Label naming: `while.cond0`, `if.then1`, `while.end2`
- Temporary naming: `%t0`, `%t1`, `%t2`, ...
- Variable naming: `%varname.addr`
- Comment format: `; function:`, `; returns:`, `; while body`
- Section markers in generated code

### Bootstrap Ladder Invariant

- weavec1 and weavec2 **must** produce identical LLVM IR
- Build fails if any divergence is detected
- Determinism is non-negotiable

## What Is Allowed to Change

### Intentional Improvements (with justification)

- Bug fixes that correct incorrect behavior
- Better error messages
- Performance optimizations (if deterministic)
- Documentation improvements

All improvements must:
- Maintain backward compatibility
- Preserve determinism
- Be justified in commit messages
- Update fixtures if output changes

### Future WIR Versions

When new features are needed:
- Introduce `(core-version 2)`
- Support both version 1 and version 2
- Never break version 1 programs
- Document migration path

## Long-Term Vision

The stabilization milestone supports the project's long-term goals:

### Auditability

Every transformation from surface language to LLVM IR is explicit and traceable:
```
Surface Code → (macroexpand) → Surface AST → (lower) → WIR → (compile) → LLVM IR
```

Each step is deterministic and inspectable.

### Determinism

The same source code will always produce the same binary:
- No randomness in compilation
- No system-dependent behavior (beyond target triple)
- No timestamp or hash-table ordering issues
- Reproducible at any future time

### Explicit Lowering

No magic or implicit behavior:
- Programmers control memory layout
- No hidden allocations
- No implicit conversions
- Clear correspondence to LLVM IR

### LLM-Friendly Structure

The entire compiler is designed to be understandable by LLMs:
- Consistent formatting and naming
- Predictable code patterns
- Clear separation of concerns
- Machine-parseable but human-readable

This enables LLM-assisted:
- Code generation
- Refactoring
- Testing
- Documentation

## Commitment

By reaching this milestone, the Weave project commits to:

- **Backward compatibility**: Valid WIR v1 programs will always compile
- **Determinism**: Same input → same output, always

This stable foundation allows innovation in the surface language while maintaining correctness guarantees at the core.

## Verification

To verify the core is stable, run:

```bash
./build.sh
```

This will:
1. Build weavec0 from LLVM IR
2. Bootstrap weavec1 using weavec0
3. Bootstrap weavec2 using weavec1
4. Run all unit tests
5. Run all integration tests
6. Run all negative tests
7. Validate LLVM IR fixtures
8. **Validate bootstrap determinism** (weavec1 == weavec2)

If the build passes, the core is stable.
